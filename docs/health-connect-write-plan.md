# Local Health Connect write plan v1

The pure planner consumes ExportJournalSnapshot detached by the existing transactional journal reader. It uses frozen stored facts, never current Preferences, a UI clock, raw GPS distance recalculation or a new workout engine. This is not a native Health Connect writer, durable outbox implementation, permission flow or exported result.

One RunningSession spans recorded UTC start through the authoritative terminal boundary, including warm-up and cool-down. Recorded manual/automatic pause exclusions become explicit intervals; planned Recovery is not a pause. The retrospective Auto interval from 0 to 10 seconds and receipt-time pause from 12 to 20 seconds remain distinct, preserving the active tail from 10 to 12 seconds. Their union must conserve the stored total active time. Missing required terminal facts or contradictory clocks yield action_required with no ready plan. Unknown zone alone does not block valid UTC; nullable start/end offsets remain honest.

Optional distance is only the stored accepted whole-run amount. Positive metres require supported GPS time; partial coverage is explicitly labelled and never spread into invented measurements. Missing optional distance/HR is omitted. HR uses valid raw local GATT-receipt UTC instants only, preserves source sequence, deduplicates identical same-instant values and rejects conflicting BPM. The v1 clock-capture guard checks boot/UTC agreement within one second where a frozen boot origin exists; it never adjusts a timestamp. No personal zones or fabricated device manufacturer/model are required. The current pure plan uses one optional HR child; native payload/chunk limits must be established before a real writer, not invented as a provider ledger here.

Client IDs contain the stable run UUID, mapping revision and record role. ClientRecordVersion is frozen mapping revision 1. SHA256 covers the exact records, eligibility provenance and warnings. Reopening a serialized fake attempt replays those IDs and payload unchanged; permission loss or failure after remote acceptance leaves incomplete state. Completion is simulated_complete, never exported. No code in this slice writes export_queue status or calls HealthConnectManager. Production retry durability, native acknowledgement and actual provider behavior remain later work under issue #4.

Framework representation is grounded in the official [ExerciseSessionRecord builder](https://developer.android.com/reference/android/health/connect/datatypes/ExerciseSessionRecord.Builder), [pause segment types](https://developer.android.com/reference/android/health/connect/datatypes/ExerciseSegmentType), [DistanceRecord builder](https://developer.android.com/reference/android/health/connect/datatypes/DistanceRecord.Builder), [HR sample](https://developer.android.com/reference/android/health/connect/datatypes/HeartRateRecord.HeartRateSample) and [client metadata](https://developer.android.com/reference/android/health/connect/datatypes/Metadata.Builder). Framework clearStartZoneOffset/clearEndZoneOffset use a system default rather than expressing unknown. A future native adapter must make its UTC-normalization/provenance choice explicit; this pure plan does not call those methods or claim unknown local time was recorded. Native builder compatibility, runtime permission behavior and real account/WHOOP outcomes are not verified here.

Mapping v1 enforces the Android API 34 representation range of 1–300 BPM for otherwise valid in-window receipts. This is a platform constraint, not a physiological or personal-zone rule: unsupported values require action and are never clamped. Platform HR timestamps use epoch milliseconds. Identical BPM values in the same millisecond retain the first source sequence deterministically; conflicting values require action. The selected sample retains its exact original receipt UTC and the journal remains unchanged; no acquisition time or extra platform precision is claimed. The [API 34 platform implementation](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/+/refs/heads/androidx-appcompat-release/android-34/android/health/connect/datatypes/HeartRateRecord.java) defines both constraints.

## SDK object adapter and terminal context

The API 34 adapter constructs real SDK session, pause-segment, distance and HR objects without acquiring a provider or calling insert/read APIs. Both frozen offsets are required; unknown legacy offsets yield action_required rather than SDK defaults. Partial measurement and receipt-time provenance is included in session notes. Construction is not provider acknowledgement or exported status.

For new runs, TerminalContext adds the observed OS zone ID, observed/effective offsets, a terminal phase-index link and versioned provenance to the existing checkpoint. All timestamps remain in the linked boundary fact. Capture occurs once in that same callback, reading the actual Android zone ID rather than a cached local zone. Effective offset is computed from the captured zone's rules at the frozen-start-derived effective UTC, so a delayed callback across DST need not use its observed offset. This does not claim that the zone was observed at the earlier effective instant. Missing rules leave null; historical plans and rows are unchanged. SQL stays at version 4 and JSON v1 permits this additive checkpoint property.

A DEBUG-only, allowlisted ranchu probe constructs clearly synthetic SDK objects and inspects getters, while the normal synthetic export guard still rejects that fixture. It writes only a private diagnostic report, never calls HealthConnectManager and requires no health permission. Actual object-runtime evidence is pending coordinated QA; compilation alone is not that evidence.
