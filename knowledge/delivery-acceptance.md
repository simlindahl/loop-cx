## Windows, emulator and delivery order
1. Pin a supported .NET SDK and compatible MAUI workload, Android SDK and JDK. Document actual versions in the repository. Install the SDK and Android emulator on Windows, create a virtual Pixel and start it. From the project, run dotnet workload restore and, if needed, the MSBuild target InstallAndroidDependencies. Use the tested explicit emulator-targeted build/install/start commands in [Android delivery](../docs/android.md); never use an unqualified run target when a personal phone is connected. Also document publishing, signing and installing the APK on a physical phone.
2. Test a vertical feature on the phone early: start the service, lock the screen, collect GPS/BLE, give an audio announcement and use a notification button. Also check that the Health Connect binding can write a test activity. Document device-specific blockers before refining the remaining UI.
3. Implement the workout engine and local storage with a deterministic clock. Add an Android emulator development mode with synthetic route, heart rate, movement/standstill and sensor loss. The agent must be able to jump directly to interval 3, standing recovery, autopause or cool-down, for example. Scenarios must start reproducibly with a documented command. Isolate test data and disable real health export for simulated sessions.
4. Connect views, favourites, speech, notification, export and map. Deliver a short test report with actual results and mark physical checks that require the runner's equipment. Do not present synthetic data as evidence of physical behavior.

### Stored History detail and route contract

The [next History data contract](integrations-data.md#stored-history-data-contract) is specified before implementation. The [exact r4 destination layouts are approved](../design/decision.md#history-details-r4-approval). Frozen Splits & phases and Time in zones are the first implementation increment; Route, new point-continuity provenance/AI v2 and actual Google SDK/configuration/rendering remain subsequent dependencies. Layout approval is not native acceptance or a claim that all details/maps or issue #4 are delivered.

- A stored multi-phase run with extensions/skips and real pauses shows the original/applied plan and actual completed active times distinctly. Elapsed is available only with sufficient effective boundary evidence; legacy absence and unsupported per-phase distance/HR remain unavailable. Main, full/final-partial splits and Total retain their own frozen values after current Settings changes and later cool-down receipts. No final split is duplicated.
- Missing/null legacy statistics and zone provenance remain unknown. Explicit supported zero, known HR outside zones and unknown HR remain distinct. Zone plus unclassified time conserves valid HR in each supported scope; no invented Below/Above allocation or RPE display.
- A new run's valid/rejected/ignored/not-assessed raw points retain stable identities and only explicitly drawable predecessors. Provider loss, actual pause and existing reanchors break links; a normal Work/Recovery transition is not independently labelled a signal gap. A callback whose `AdvanceClock` finishes the run or whose source is not assessed has the correct explicit not-assessed/finalization outcome and no drawable link; no frozen raw record or terminal batch is mutated to attach a later assessment or stale quality. Displayed raw route evidence never becomes accepted distance or Ghost verification.
- A genuine schema-6 fixture gains only the specified nullable provenance column; its existing columns, cells and rows are preserved and old provenance remains null. Injected transaction failure, identical retry, uncertain local commit result and cold reopen preserve each committed raw/provenance pair exactly once. Process death exposes only the committed prefix, not a reconstructed RAM tail or stop time. Existing native exception/retry classifications remain explicit.
- Existing v1 AI samples/consumers retain their documented contract. New v2 schema/projector/sample and the independent parser reconstruct identical frozen/raw facts plus optional point provenance, including absent/null legacy, valid links and rejected unsupported/cross-run/forward references. Migration or map viewing does not rewrite old JSON or journal facts.
- For the same eligible source before/after the additive change, HC mapping-v1 ordered records, notes/warnings, IDs/version and payload hash are identical. An existing durable attempt reclaims and validates its ACK with that same frozen payload; no route fact, JSON version change, fake success or missing map key creates or changes production Exported.
- Later native acceptance verifies same-ID detail/Back and active-owner navigation, offline/reopen, true route breaks and explicit legacy-unknown quality, plus 200% text/focus/TalkBack/reduced motion against the approved layout once decided. No key/network/SDK availability may block stored facts, recording or export. Positive map rendering requires its separately configured Google SDK environment; a ready SDK object alone does not establish visible map tiles. No Cloud/key/permission/provider action is part of this documentation checkpoint.

## Acceptance tests
| Test | Expected result |
|---|---|
| Start the same favourite twice on separate occasions, then edit the favourite | One tap per start. Two separate runs with their original plans in history. |
| 3 min warm-up, 5 × 3 min work with 2 min recovery, 2 min cool-down | 5 work phases, 4 recoveries, main-set time 23 min, total 28 min. Exactly one export of the whole run. |
| +1 min twice, then skip the rest of the warm-up | Planned end moves by 120 s. Actual warm-up is saved and main-set counters start at zero. The same extension works during cool-down. |
| 2.4 km continuous main set with coaching every 500 m | Four distance-triggered reports; splits of 1 km, 1 km and 0.4 km. No warm-up distance is counted. |
| 29 s pace deviation followed by a new split, then 30 s deviation | No time carries into the new split. One announcement when the new deviation reaches 30 s. Also test zone, exact pace threshold and heart-rate loss. |
| Stop during work, standing recovery, manual pause | Autopause after ten seconds of confirmed standstill during work, retrospectively subtracting the full ten-second confirmation window from active training time and automatic resume on movement. Timed recovery expires despite standstill. Distance recovery ends only at the correct distance. Manual pause requires explicit resume. |
| Disconnect heart rate, lose GPS, phone has no internet | No invented heart rate or distance. A timed workout continues. Gaps appear in export. Saved history opens offline. |
| Finish with health export denied, reopen the app, grant permission and retry twice | Local session exists immediately. One exported running activity after retry; no duplicate distance or heart-rate records. |
| Share JSON and read it with an independent parser | Reconstruct phase order, main-set time and total distance from the time series/phases within documented rounding. |
| Pixel + WHOOP, Spotify, locked screen during a real run | GPS and heart rate continue, audio is audible, mini-UI controls the correct phase and opening the app resumes the same view. Check music volume and record battery use per hour. |
| Health Connect → WHOOP | Verify one activity with correct start/end and distance. Document its actual effect on each runner goal and any conflict with WHOOP autodetection. |

### Measured statistics coverage

Use the [sample-bracketed statistics contract](running-workouts.md#measured-statistics-coverage-contract) for the next timed C1/C2 service/journal slice: known plus unknown equals active time in total/main/current/final splits, no edge/end extrapolation, exact autopause exclusion and honest null pace/heart rate.
