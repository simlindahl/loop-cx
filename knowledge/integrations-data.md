# Integrations, storage and data

[Product entry point and ownership](product.md). M1 requirements unless explicitly marked otherwise.

<a id="integration-lagring-och-fel"></a>
## Integration, storage and errors
- **WHOOP.** Read the band's Bluetooth LE heart rate with heart-rate broadcast enabled. Let the user connect the band on first use and enter personal zones. Verify ordered boundaries without unintended gaps or overlaps. Reconnect after interruption. Show a dash for missing heart rate, continue the workout and suppress heart-rate coaching until new readings arrive. Live recording requires no WHOOP web API or custom cloud service.
- **Android.** Request precise location and the relevant Bluetooth scan/connect permissions when the features are used. Declare foreground service types and permissions required by the selected Android version for location and a connected device. Start the service from a visible app. Request notification permission for the mini-UI. If access is denied, show the consequence and a path to settings. Continue with available features. A timed workout can work without GPS; explain and let the user change the plan when distance is essential.
- **Local database.** Save favourites, settings, the frozen workout plan and zones, phase boundaries, raw sensor readings, pauses, quality markers and export status. Write continuously during the workout. After process death, the user must at least be able to save the recorded part with an interruption marker. Never add unsupported time or distance. Finishing must atomically finalize the session and enqueue export.
- **Health Connect.** Request write permissions when integration is enabled. Automatically export a running session for the whole run, distance and available heart-rate data. Use stable external record IDs for the session and child records. Retry safely after interruption or changed permissions. Show pending/exported/action required. Exported means written to Health Connect. WHOOP imports separately and uses its own heart-rate readings. Check with a real account how workout count, time, distance and time in zones are credited and whether duplication occurs. Importing other apps' workouts is outside v1.
- **Map.** Google Maps SDK for Android shows the local GPS track in ordinary workout history. [Ghost Run live map](ghost-run.md#live-map-audio-and-locked-screen) is the explicit separate exception; its route/runner/reference behavior does not add a general live map to ordinary workouts. The standard SDK has unlimited free use according to the current pricing list but requires a Google Cloud project with billing and an API key. Restrict the key to the Android package/signature and correct API. Recording, statistics and export must work without network access or a map key. Show clear map status.
- **AI export.** Share one UTF-8 JSON file per run through Android's share sheet. Version the schema. Include stable session ID, UTC timestamps and local time zone, plan with all targets and zones, actual phases/splits, active and elapsed time, total and main set, zone statistics, GPS with accuracy, heart rate, pauses, data gaps and manual phase changes. Specify units explicitly and distinguish measured from derived values. Use null for unknown. Deliver a schema and a small sample file the agent can validate. Coordinates are included in the full export.

## Service-owned BLE heart-rate storage

The HR backend uses a selected device address and explicit personal zones from one versioned local configuration. There is no new production pairing or zone editor in this slice. RunService reads and validates that configuration only when accepting a new run, freezes a copy in `runs.heart_rate_metadata`, and owns the GATT source, callbacks, reconnect attempts and cleanup. Repeated starts do not replace it. Standard HR notifications carry no acquisition timestamp: `heart_rate.receipt_utc` and `receipt_monotonic_ticks` describe local callback receipt, not a time reconstructed from RR values.

SQLite schema 4 adds the append-only `heart_rate` table and nullable `runs.heart_rate_metadata`. Raw BPM-or-null/quality and the corresponding derived checkpoint commit in one transaction. Existing schema 1–3 rows retain their plans, checkpoints, raw GPS and events; absent metadata means unknown legacy configuration. Process restart still marks an unfinished run interrupted rather than inventing recovery time.

API 33 and later use the value-bearing GATT callback and descriptor write. API 26–32 use the guarded legacy callback and descriptor write with the same copied payload and local receipt clocks. Permission denial, contact loss, adapter failure and exhausted reconnect attempts also preserve the workout. Reconnect is restricted to the selected source, with three attempts per interruption and no broad background scan. Physical WHOOP validation, approved connection/zone Settings UI and actual legacy Android runtime verification remain acceptance work; debug feasibility logs are not production evidence.

The API 26–30 selected-device connection uses the legacy normal `BLUETOOTH` manifest permission, capped at SDK 30; it adds no new runtime prompt or scan permission. API 31+ uses the existing `BLUETOOTH_CONNECT` runtime permission. The version guards follow Android's [GATT callback](https://developer.android.com/reference/android/bluetooth/BluetoothGattCallback) and [descriptor-write](https://developer.android.com/reference/android/bluetooth/BluetoothGatt#writeDescriptor(android.bluetooth.BluetoothGattDescriptor,%20byte[])) contracts. Android API 26–32 runtime evidence remains separate from compilation of those paths.

Invalid, unsupported or malformed optional HR preferences are preserved unchanged for later repair. A valid Core workout starts with a disabled HR source, no inferred zones and an explicit `configuration-invalid` state/error in the frozen HR setup/checkpoint. This fallback does not replace the saved preference or turn invalid sensor data into valid readings. Production GATT cleanup runs on finalization and destruction throughout API 26+, independently of the newer DEBUG feasibility-probe guards.


### Local JSON foundation

The first JSON backend slice reads one run, its outbox status, ordered events, raw GPS and raw HR inside one SQLite transaction. Projection performs no writes and uses no current Preferences, clock or workout factory. This is a consistent storage snapshot, not a common sensor-callback cutoff: existing raw GPS may precede the last derived checkpoint, and its observation must remain separate rather than fabricated into those counters. Version 1 preserves the stored original plan, resolved checkpoint, frozen targets/zones and final main/split statistics; it does not recompute final results from later raw data. A machine-readable schema, synthetic sample and independent parser define the local file contract. Android sharing and normal Health Connect delivery remain separate work under issue #4.

For new runs, freeze the start's local time-zone identifier, UTC offset and boot-monotonic anchor. Store this nullable start context and an append-only logical list of typed phase-boundary facts in the existing checkpoint JSON. No database-version change is needed. Each fact identifies previous/next phase instances, effective run-relative monotonic elapsed, actual observed run-relative elapsed/UTC, start-anchor-derived effective UTC and synthetic provenance. A terminal transition is a boundary, not an invented finish-cause taxonomy. Capture at the existing service transition seam, after distance/main finalization; never infer an unrecorded legacy boundary. Legacy absent context/facts remain unknown.

The service retains the cumulative boundary list across failed persistence. A checkpoint transaction stores the entire list with the resulting state, so retries neither lose facts nor append duplicates. Existing raw observations and command rows remain immutable; new checkpoint fields do not relabel old plans or clock columns. Observed elapsed/UTC remain observations, while effective UTC is explicitly derived from the frozen start anchor. DEBUG acceleration remains labelled synthetic and its export queue stays disabled.

Acceptance includes deterministic repeated projection, explicit units and nulls, independent reconstruction of frozen plans/statistics, stable raw/event order and an internally consistent read during concurrent checkpoints. Verify interrupted/legacy rows without invented end times, main finality through later cool-down observations, and atomic boundary/state retention. This foundation does not claim provider delivery, physical WHOOP credit or a share UI.


### Local Health Connect write-plan boundary

The next backend slice creates a frozen version-1 write plan from a detached journal snapshot only. One running session spans the complete recorded start/end interval, including warm-up and cool-down; actual pause exclusions remain explicit segments rather than shortening that parent window or treating recovery as a pause. Optional distance is the accepted stored whole-run amount, with partial coverage described honestly; no raw-coordinate recomputation, uniform distribution or extrapolation is added. Optional HR contains only valid stored raw callback receipts inside the window, not held/interpolated samples or invented acquisition times. Personal zones are not required to export valid raw HR.

A valid finalized start/end and consistent monotonic boundary provenance are mandatory. Missing, contradictory or unfinished timing yields action_required and no writer calls. Synthetic/debug recordings are rejected both by planning and replay. Unknown historical local-zone provenance remains null in the pure plan and does not itself invalidate sound UTC; a future native adapter must not silently replace unknown offsets with the current system zone. The framework clear-offset methods use a system default, so their native mapping remains an explicit adapter obligation.

Freeze deterministic session/child client record IDs, mapping version and a hash of the actual payload before retry. A compact serializable fake attempt proves permission loss, partial remote success and remote-accepted/local-ack-lost replay with the same identities. Fake completion is named simulated_complete, never exported; this slice neither changes production outbox status nor adds a provider ledger, permission UI, SDK insert call, account or server. Actual Health Connect acknowledgement and Android durability remain later acceptance under issue #4.


Mapping v1 checks stored start-monotonic anchors for agreement and cross-checks valid HR receipt UTC against its stored boot receipt when that anchor exists. Its one-second capture/clock-disagreement tolerance is an explicit engineering guard, not a sensor-quality or physical accuracy promise; it never shifts a stored timestamp. A receipt inside only one clock window, or a larger disagreement inside both, requires action. Exact retrospective automatic-pause intervals remain separate from receipt-time pause intervals, preserving the supported active tail. Positive accepted metres with zero supported GPS time is contradictory rather than missing distance.
