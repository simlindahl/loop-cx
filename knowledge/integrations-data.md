# Integrations, storage and data

[Product entry point and ownership](product.md). M1 requirements unless explicitly marked otherwise.

<a id="integration-lagring-och-fel"></a>
## Integration, storage and errors
- **Heart-rate connection.** Let the user deliberately select a compatible standard Bluetooth LE Heart Rate service sensor on first use and configure personal zones as specified below. WHOOP with heart-rate broadcast enabled is one supported target, not the feature's identity or a promise of compatibility with every watch, ANT+ or cloud service. Reconnect after interruption. Show unavailable for missing heart rate, continue the workout and suppress heart-rate coaching until valid readings arrive. Live recording requires no WHOOP web API or custom cloud service.
- **Android.** Request precise location and the relevant Bluetooth scan/connect permissions when the features are used. Declare foreground service types and permissions required by the selected Android version for location and a connected device. Start the service from a visible app. Request notification permission for the mini-UI. If access is denied, show the consequence and a path to settings. Continue with available features. A timed workout can work without GPS; explain and let the user change the plan when distance is essential.
- **Local database.** Save favourites, settings, the frozen workout plan and zones, phase boundaries, raw sensor readings, pauses, quality markers and export status. Write continuously during the workout. After process death, the user must at least be able to save the recorded part with an interruption marker. Never add unsupported time or distance. Finishing must atomically finalize the session and enqueue export.
- **Health Connect.** Request WRITE permissions only when integration is enabled. Automatically export a running session for the whole run, distance and available heart-rate data. Use stable external record IDs for the session and child records. Retry safely after interruption or changed permissions. Show pending/exported/action required, including honest partial, unavailable, denied and revoked states. Exported requires confirmed provider acknowledgement of every required record; enabling integration is not acknowledgement for any run. Local data remains available. WHOOP imports separately and uses its own heart-rate readings. Check with a real account how workout count, time, distance and time in zones are credited and whether duplication occurs. No READ permission, other apps' workout import or automatic WHOOP credit is implied.
- **Map.** Google Maps SDK for Android shows the local GPS track in ordinary workout history. [Ghost Run live map](ghost-run.md#live-map-audio-and-locked-screen) is the explicit separate exception; its route/runner/reference behavior does not add a general live map to ordinary workouts. The standard SDK has unlimited free use according to the current pricing list but requires a Google Cloud project with billing and an API key. Restrict the key to the Android package/signature and correct API. Recording, statistics and export must work without network access or a map key. Show clear map status.
- **AI export.** Share one UTF-8 JSON file per run through Android's share sheet. Version the schema. Include stable session ID, UTC timestamps and local time zone, applicable plan/targets/zones, actual phases/splits, active and elapsed time, total and main set, zone statistics, GPS with accuracy, heart rate, pauses, data gaps and manual phase changes. Specify units explicitly and distinguish measured from derived values. Use null for unknown. Deliver a schema and a small sample file the agent can validate. Disclose precise coordinates and other sensitive content before sharing the full file. Opening or cancelling the sheet changes neither local data nor Health Connect state and proves no recipient delivery. No redaction mode, automatic send or new recipient service is added.

## Personal heart-rate zones

The approved form has two positive whole-BPM inputs: resting heart rate and maximum heart rate, with maximum greater than resting. Calculate heart-rate reserve (HRR) as maximum minus resting. The five lower thresholds are the ceiling of `resting + p × HRR` for 40%, 60%, 70%, 80% and 90%. Use exact rational/integer arithmetic rather than floating-point inflation at an integer boundary. Each zone ends one BPM below the next lower threshold; Zone 5 ends at the entered maximum. Reject collapsed or non-increasing integer ranges. These are arithmetic checks, not invented clinical limits or an age-based estimate.

Preview the five ranges read-only, plus Below Zone 1 and Above configured maximum. Valid readings outside the bounded zones remain known HR with unclassified zone time; they are distinct from missing/invalid readings and unknown HR time. The form adds no automatic resting-HR acquisition, monthly recalculation or manual-override mode. The method follows the HRR family, not guaranteed exact vendor calibration, rounding or import.

Saving changes future starts only. Freeze method ID/version, input/configuration revision, exact resting/maximum inputs, percentage/rounding policy and resolved integer boundaries with each run. Preserve old manually configured ranges and unknown provenance verbatim; never recalculate history or backfill an unknown method. The [approved Settings reference](../design/mockups/settings-integrations/index.html) illustrates the form, not working sensor or medical acceptance.

## Interrupted recordings and storage failures

Recovery saves only the supported recorded part under its original stable run ID, retaining the original plan, observations and interruption provenance. The last committed checkpoint observation is not the actual stopping time. Do not resume the old timer, manufacture a finish or add unsupported time/distance. Show saved detail only after local commit; retry the same operation/ID without a duplicate. Missing required Health Connect end provenance is not invented by local saving.

A live storage failure belongs to the service state and appears inline with Retry saving and the existing Pause/Resume controls. Do not silently autopause or add a separate Continue mode. Warn that recent unsaved data may be lost if the app closes; do not promise unlimited memory recovery. Running copy is conditional on the actual service state. Clear an error only after successful commit, and do not claim completion/export while final persistence has failed. An irrecoverable open/read failure must not offer an unsupported retry or running message. Unattended backoff, discard rules and starting a competing run are not introduced by this flow. The [approved recovery/error reference](../design/mockups/health-export/index.html#recording-recovery-proposal) requires real commit/repeated-failure verification during implementation.

## Activity provenance

Frozen history, JSON and future Health Connect plans distinguish a [Ghost race](ghost-run.md#race-identity-and-applicability) from its source recording and from Core templates. Race snapshots carry an activity kind/schema revision and route/version, frozen reference and race-rule provenance. RPE and optional pace/zone targets are explicitly not applicable, represented by the versioned contract as null/absent rather than RPE 0 or a fabricated C2 template. Reusing a C2-derived route never rewrites that source session's original RPE, template or export. Exact field names belong to the owning model/schema; preserve historical Core and archive records.

## Service-owned BLE heart-rate storage

The HR backend uses a selected device address and explicit personal zones from one versioned local configuration. There is no new production pairing or zone editor in this slice. RunService reads and validates that configuration only when accepting a new run, freezes a copy in `runs.heart_rate_metadata`, and owns the GATT source, callbacks, reconnect attempts and cleanup. Repeated starts do not replace it. Standard HR notifications carry no acquisition timestamp: `heart_rate.receipt_utc` and `receipt_monotonic_ticks` describe local callback receipt, not a time reconstructed from RR values.

An explicit OS device choice persists a selected source for the next run; it is not evidence of an active connection or fresh HR. Opening Settings or choosing a sensor without a run starts neither GATT nor a RunService workout. Connected/fresh-HR status comes only from the same active service's frozen source. If sensor A is active and the user selects B for future starts, keep those identities distinct and never attribute A's readings to B. Synthetic connected states in the design reference illustrate presentation, not a standalone Settings connection or sensor measurement.

SQLite schema 4 adds the append-only `heart_rate` table and nullable `runs.heart_rate_metadata`. Raw BPM-or-null/quality and the corresponding derived checkpoint commit in one transaction. Existing schema 1–3 rows retain their plans, checkpoints, raw GPS and events; absent metadata means unknown legacy configuration. Process restart still marks an unfinished run interrupted rather than inventing recovery time.

API 33 and later use the value-bearing GATT callback and descriptor write. API 26–32 use the guarded legacy callback and descriptor write with the same copied payload and local receipt clocks. Permission denial, contact loss, adapter failure and exhausted reconnect attempts also preserve the workout. Reconnect is restricted to the selected source, with three attempts per interruption and no broad background scan. Physical WHOOP validation, approved connection/zone Settings UI and actual legacy Android runtime verification remain acceptance work; debug feasibility logs are not production evidence.

The API 26–30 selected-device connection uses the legacy normal `BLUETOOTH` manifest permission, capped at SDK 30; it adds no new runtime prompt or scan permission. API 31+ uses the existing `BLUETOOTH_CONNECT` runtime permission. The version guards follow Android's [GATT callback](https://developer.android.com/reference/android/bluetooth/BluetoothGattCallback) and [descriptor-write](https://developer.android.com/reference/android/bluetooth/BluetoothGatt#writeDescriptor(android.bluetooth.BluetoothGattDescriptor,%20byte[])) contracts. Android API 26–32 runtime evidence remains separate from compilation of those paths.

Invalid, unsupported or malformed optional HR preferences are preserved unchanged for later repair. A valid Core workout starts with a disabled HR source, no inferred zones and an explicit `configuration-invalid` state/error in the frozen HR setup/checkpoint. This fallback does not replace the saved preference or turn invalid sensor data into valid readings. Production GATT cleanup runs on finalization and destruction throughout API 26+, independently of the newer DEBUG feasibility-probe guards.


### Local JSON foundation

The first JSON backend slice reads one run, its outbox status, ordered events, raw GPS and raw HR inside one SQLite transaction. Projection performs no writes and uses no current Preferences, clock or workout factory. This is a consistent storage snapshot, not a common sensor-callback cutoff: legacy raw GPS may precede the last derived checkpoint, and its observation must remain separate rather than fabricated into those counters. New service-owned save batches commit pending raw GPS/HR and event facts with their checkpoint; this does not backfill older recordings. Version 1 preserves the stored original plan, resolved checkpoint, frozen targets/zones and final main/split statistics; it does not recompute final results from later raw data. A machine-readable schema, synthetic sample and independent parser define the local file contract. Android sharing and normal Health Connect delivery remain separate work under issue #4.

For new runs, freeze the start's local time-zone identifier, UTC offset and boot-monotonic anchor. Store this nullable start context and an append-only logical list of typed phase-boundary facts in the existing checkpoint JSON. No database-version change is needed. Each fact identifies previous/next phase instances, effective run-relative monotonic elapsed, actual observed run-relative elapsed/UTC, start-anchor-derived effective UTC and synthetic provenance. A terminal transition is a boundary, not an invented finish-cause taxonomy. Capture at the existing service transition seam, after distance/main finalization; never infer an unrecorded legacy boundary. Legacy absent context/facts remain unknown.

The service retains the cumulative boundary list across failed persistence. A checkpoint transaction stores the entire list with the resulting state, so retries neither lose facts nor append duplicates. Existing raw observations and command rows remain immutable; new checkpoint fields do not relabel old plans or clock columns. Observed elapsed/UTC remain observations, while effective UTC is explicitly derived from the frozen start anchor. DEBUG acceleration remains labelled synthetic and its export queue stays disabled.

Acceptance includes deterministic repeated projection, explicit units and nulls, independent reconstruction of frozen plans/statistics, stable raw/event order and an internally consistent read during concurrent checkpoints. Verify interrupted/legacy rows without invented end times, main finality through later cool-down observations, and atomic boundary/state retention. This foundation does not claim provider delivery, physical WHOOP credit or a share UI.


### Disclosed Android JSON sharing

Finished stored details and an interrupted recording with a confirmed local-save acknowledgement offer Share workout data. Recheck that eligibility and read the recording, outbox and acknowledgement inside the same detached journal transaction. A current active or failed-final-save owner and an unconfirmed interrupted prefix are not share sources. Another running session continues unchanged. Prepare new normal share files through the version-2 projection, including legacy recordings with absent or null point provenance. Preserve the explicit version-1 diagnostic projection and existing version-1 files and consumers. Keep raw order, frozen historical targets and unknown end provenance; the recovery acknowledgement is not added as an original recording fact.

The approved disclosure names precise GPS coordinates and UTC timestamps, heart rate, the frozen plan and targets, phases/splits, pauses and gaps before the explicit Open Android share sheet action. Back returns to the same detail and opener. Cancelling preparation prevents a late handoff; cancelling or returning from Android changes neither the recording nor Health Connect state. A successful share API return only establishes that the chooser was requested, not a recipient, read or delivery.

Prepare one complete UTF-8 JSON file in an operation-unique private cache directory before granting read access. Restrict the Android FileProvider to this slice's cache subtree and use application/json with a temporary read grant; expose no database, preferences, external storage or broad cache root. Retain prepared files after requesting the chooser because Android may return before a recipient reads them. A later explicit share may clean only this slice's recognized cache entries older than seven days, outside any current preparation; Android may independently evict cache. File preparation or chooser failure stays inline with retry and no partial-file handoff. Normal Health Connect dispatch, redaction and automatic sending remain outside this slice.

### Local Health Connect write-plan boundary

The next backend slice creates a frozen version-1 write plan from a detached journal snapshot only. One running session spans the complete recorded start/end interval, including warm-up and cool-down; actual pause exclusions remain explicit segments rather than shortening that parent window or treating recovery as a pause. Optional distance is the accepted stored whole-run amount, with partial coverage described honestly; no raw-coordinate recomputation, uniform distribution or extrapolation is added. Optional HR contains only valid stored raw callback receipts inside the window, not held/interpolated samples or invented acquisition times. Personal zones are not required to export valid raw HR.

A valid finalized start/end and consistent monotonic boundary provenance are mandatory. Missing, contradictory or unfinished timing yields action_required and no writer calls. Synthetic/debug recordings are rejected both by planning and replay. Unknown historical local-zone provenance remains null in the pure plan and does not itself invalidate sound UTC; a future native adapter must not silently replace unknown offsets with the current system zone. The framework clear-offset methods use a system default, so their native mapping remains an explicit adapter obligation.

Freeze deterministic session/child client record IDs, mapping version and a hash of the actual payload before retry. A compact serializable fake attempt proves permission loss, partial remote success and remote-accepted/local-ack-lost replay with the same identities. Fake completion is named simulated_complete, never exported; this slice neither changes production outbox status nor adds a provider ledger, permission UI, SDK insert call, account or server. Actual Health Connect acknowledgement and Android durability remain later acceptance under issue #4.


Mapping v1 checks stored start-monotonic anchors for agreement and cross-checks valid HR receipt UTC against its stored boot receipt when that anchor exists. Its one-second capture/clock-disagreement tolerance is an explicit engineering guard, not a sensor-quality or physical accuracy promise; it never shifts a stored timestamp. A receipt inside only one clock window, or a larger disagreement inside both, requires action. Exact retrospective automatic-pause intervals remain separate from receipt-time pause intervals, preserving the supported active tail. Positive accepted metres with zero supported GPS time is contradictory rather than missing distance.

Mapping v1 enforces the Android API 34 representation range of 1–300 BPM for otherwise valid in-window receipts. This is a platform constraint, not a physiological or personal-zone rule: unsupported values require action and are never clamped. Platform HR timestamps use epoch milliseconds. Identical BPM values in the same millisecond retain the first source sequence deterministically; conflicting values require action. The selected sample retains its exact original receipt UTC and the journal remains unchanged; no acquisition time or extra platform precision is claimed.

### Android record construction without provider delivery

The next adapter constructs actual API 34 Health Connect record objects from an eligible frozen write plan, without obtaining a HealthConnectManager or calling a provider. Missing frozen start/end offsets require action; the adapter never supplies a current system zone or invented UTC offset. Normal debug, synthetic, unfinished and altered-hash plans remain blocked. A separately guarded disposable-emulator test may construct explicitly synthetic SDK objects only; it cannot insert records or mark production export successful.

New terminal-zone context is optional checkpoint metadata captured once at the actual terminal boundary. Existing plans, raw data, elapsed columns and database version 4 remain unchanged. Legacy absent facts stay unknown. JSON version 1 already permits additive checkpoint properties; no new export format or migration is required. Acceptance distinguishes SDK object construction from provider permission, insertion, acknowledgement and retry durability, which remain later work.

TerminalContext links the existing terminal boundary by its previous phase index and adds only the observed zone identifier, observed offset, effective offset and versioned provenance. Both offsets are calculated from the same OS zone captured at that callback, at the boundary's recorded observed/effective UTC instants respectively. The effective offset is a derivation from the observed terminal zone's rules, not evidence that the zone was observed earlier. Missing rules leave the context unknown. The frozen context is never refreshed at delivery time; malformed links or unsupported provenance require action.

### Normal selected-source and HRR Settings slice

Settings is a real destination from Training, including during a timed run. Selecting a standard BLE Heart Rate sensor uses Android's permission and filtered system chooser. Cancellation or denial leaves the saved source unchanged; a successful deliberate choice saves a selected source for future starts, not a claim that a connection exists. Empty Settings starts no service or GATT owner. Connected/fresh status belongs only to the active service's actual frozen source. Selecting B while A is active cannot attribute A's readings to B or replace A's configuration. Removing a selection applies to future starts as labelled.

The HRR form starts blank without a saved HRR profile; valid legacy manual ranges remain unchanged until explicit Save. Save freezes method/version, a configuration revision, the two entered inputs, ceiling policy and exact resolved boundaries with subsequent starts through the existing service setup. Cancel discards the draft. The local color overview is read-only and shows HRR proportions, with a persistent exact-BPM legend; it is not measured zone time. Values outside the ranges remain known unclassified HR rather than missing data. This slice adds no default pulse values, automatic measurement/import, always-on Settings connection, audio, History placeholder, provider integration or new health permission. Native selection/permission/cancel, frozen-source/profile behavior, persistence and accessibility remain independent acceptance checks.

### Durable Health Connect attempt boundary

Database version 5 adds nullable attempt_json and last_error to the existing export_queue. Existing IDs/statuses and all run facts remain unchanged. Preparing an eligible finished run reads a consistent detached snapshot and freezes its complete versioned plan/hash/client identities in the same transaction that claims a fresh attempt token. Retrying reuses that frozen payload, never current Settings. One process-owned dispatch gate prevents overlapping local dispatch; restart may reclaim an unfinished attempt with a new token. No timed lease, child ledger or background framework is added.

Release the SQLite transaction before any external call. Check every WRITE grant needed by the frozen batch before its first insert; missing optional measurements require no corresponding grant, but a present child cannot be silently dropped. Treat partial/failed remote acceptance as unacknowledged and retry the exact client IDs/version. Only a validated actual SDK response for every intended type/client ID/version, with assigned provider IDs, may atomically record acknowledgement and exported. Token/hash checks apply to success and failure callbacks; stale or duplicate callbacks cannot overwrite a newer attempt. A crash after remote acceptance but before local commit remains retryable with the same payload.

Malformed, unsupported, inconsistent or tampered attempts require action without writer calls. Normal DEBUG/synthetic/unfinished sources remain independently blocked even if queue status is corrupt. Controlled scratch simulations retain synthetic provenance and disabled production status; simulated_complete never means provider acknowledgement or exported. No normal integration UI, runtime permission prompt, provider execution or automatic dispatch is enabled in this slice. Positive session/distance/HR provider fixtures require the separate [14 November expanded isolated approval](../design/decision.md#expanded-isolated-health-connect-verification-approval--14-november-2026); the earlier exercise-only probe consent remains insufficient.

### Service-owned save and explicit retry boundary

The running service retains immutable uncommitted GPS scalars, HR receipts and original command/event checkpoint facts, plus the latest checkpoint. A failed transaction leaves that batch pending; subsequent live observations and controls remain owned by the same run. After failure, only explicit Retry saving attempts persistence again. Clear pending facts/error only after EndTransaction succeeds. A frozen failed batch is retried before later observations; a checkpoint save revision detects an already committed identical batch if the local completion outcome was uncertain, without duplicating raw rows/events.

Terminal capture occurs once. A failed final commit keeps the service and original terminal checkpoint available for retry, with no Saved confirmation, export activation or competing start. Retry does not advance a finished clock or recapture terminal times/zone. Successful final commit permits the existing local-save acknowledgement and return to Training. An unexpected process death still loses uncommitted RAM data; only the committed prefix is available under existing interruption semantics. No unlimited memory/durability claim is made. An initial database-open failure reports that training did not start and does not offer a nonfunctional Retry saving action. Malformed or conflicting stored checkpoint/revision data remains unchanged and yields a nonretryable storage-unavailable state, without a running claim or automatic repair. Known native SQLite corruption/cannot-open failures have the same nonretryable outcome; checkpoint-read disk-I/O or access-permission failures are also classified before any replacement write. Ordinary transaction ABORT, busy/full and other transient write failures remain retryable.

The journal explicitly supplies a non-destructive Android DatabaseErrorHandler. It throws the native corruption exception without delegating to the default file-deleting handler or returning into Android's automatic reopen attempt. The normal helper has no obsolete-schema deletion/reset policy. A dedicated DEBUG scratch probe uses the same helper and handler, closes a valid scratch database before replacing only its uniquely owned file with nonempty invalid bytes, and requires two failed opens with unchanged main/sidecar hashes and a nonretryable state. Native corruption preservation is NOT RUN until independent QA; ordinary journal files are never corrupted for this test.

### Finished-run History read boundary

History lists committed finished runs newest first and opens a detached stored detail under the same stable ID. Queries/projections do not use current Core or HR Settings and never rewrite old rows. Main/total/final split statistics, resolved plan/targets, source revision and HR setup remain the frozen checkpoint facts; unknown legacy fields remain Unavailable. Main elapsed requires sufficient actual phase-instance boundary facts, including Work/Recovery and real pauses. Missing end/phase facts are not replaced with planned durations or last observation time. Exported requires a consistent acknowledged durable attempt, while disabled_synthetic remains explicitly not exported.

Training, History and Settings navigation keeps an active service/run intact; list/detail data load on navigation rather than each clock tick. Saved View run appears only after the local commit. Finished detail remains separate from interrupted-prefix recovery below. The archive distinguishes unreadable/interrupted recordings from an actually empty list. Sharing, map and provider actions remain outside this local History/recovery slice. Read failures preserve bytes and show an unavailable/error state without repair. Native offline/reopen, frozen-history, same-run navigation and accessibility checks remain separate acceptance.

Notification entry is bound to the current service-owned run ID. A tap returns from History or Settings to that same run; stale IDs and entries without a live matching owner do not recreate or redirect a recording. The entry is consumed once across warm or recreated Activity delivery, and does not change commands, save state or the recording identity.

### Stored detail facts and route continuity

This is the bounded History data contract under [#4](https://github.com/simlindahl/loop-cx/issues/4). Merged PR107 delivered frozen Splits & phases and Time in zones; merged PR109 delivered schema7 point provenance and normal AI v2 sharing. The owner has [approved the exact r4 detail layouts](../design/decision.md#history-details-r4-approval). Those stored views retain Back/focus return. Route projection and actual Google SDK/configuration/rendering remain subsequent dependencies; no placeholder Route action or fabricated SDK state is introduced. This does not complete issue #4. Compact split tables use an accessible em dash and visible legend for missing metrics; expanded large-text blocks retain the full unavailable label. The existing 21-em reflow threshold compares actual container width with computed rendered font size, including Android WebView TextZoom, using one component-owned ResizeObserver with initial/resume refresh and stable-token disposal cleanup that does not depend on resolving an already removed DOM element; it changes no recorded values.

**Frozen detail facts.** Read the existing detached journal transaction, not current Settings or a serialize-and-reparse projection. Keep final Main and split statistics authoritative even when later cool-down HR supported more Total time. Match `Snapshot.Distance.Splits` to `Snapshot.Statistics.CompletedSplits` in stored order, including the final partial split once; do not duplicate it with `CurrentSplit` or silently distribute Main totals across missing splits. Active time, accepted metres, strict nullable average pace, weighted average HR and GPS/HR known/unknown coverage retain their stored scopes and units.

Phase instances retain original order. `Completed[index].ActiveTime` is actual recorded active time when the completed instance is valid; it does not depend on boundary availability. Keep original planned duration distinct from the applied `Plan` duration, which may include extensions, and from shorter actual work after a skip. Per-phase elapsed requires matching effective start/end boundary facts, with zero as the first phase's start; observed callback time is not an effective boundary. Missing legacy boundaries remain unavailable, not planned duration or active time presented as elapsed. Per-phase distance, pace, HR and zone aggregates are not currently frozen scopes and remain unavailable; no replay of raw data or allocation of whole-run totals is authorised to manufacture them. Synthetic time remains labelled as such.

Main and Total zone durations use their respective stored `HeartRateZones`, valid-HR time, unknown-HR time and `UnclassifiedHeartRateActiveTime`, together with that run's frozen personal boundaries/method where recorded. Known HR outside configured zones is distinct from missing HR. The single unclassified duration cannot be divided into Below Zone 1 and Above maximum. Absent configuration or method is not today's HRR profile. Preserve actual JSON field presence: a missing/null legacy statistic is unavailable, not a default-valued DTO's zero. An explicit empty zone-duration array may establish zero only with sufficient supported scope/configuration facts and conservation; null does not. Do not display RPE or rewrite historical raw values.

**New raw-point provenance.** The pre-PR109 baseline was journal schema6 without per-point GPS acceptance/continuity. Delivered additive schema7 provides one nullable, versioned provenance value per new `locations` row, carried by the existing immutable `RunSaveLocation` and `CommitTransaction`, rather than a separate ledger. Its contract contains a stable per-run point identity, an explicit valid/rejected/ignored/not-assessed outcome, a nullable earlier point identity that may be joined for display, and a technical break reason when applicable. The existing SQL row order/coordinates/clocks/accuracy retain their meanings. Old rows retain null; neither migration nor History backfills a guessed assessment or predecessor.

Copy raw scalar values on receipt. In the current seam, `AdvanceClock`/`RecordPhaseBoundary` update owner facts without committing; determine this callback's outcome after that clock update and freeze it with the raw record before the later `Publish`/save. If the clock has finished the run, use explicit not-assessed/finalization with no drawable predecessor instead of performing a new distance assessment. Once the batch is frozen, no late classification may mutate its raw record or terminal facts. A point not assessed during Auto pause, unavailable source or finish cannot inherit a previous `DistanceObservation`. Duplicate/out-of-order outcomes are explicit, not silently relabelled valid. A drawable predecessor must exist earlier in the same run and supported chain; it cannot cross an actual owner pause, provider interruption, quality rejection or reanchor. Capture existing reanchor semantics: Work/Recovery can retain their existing continuous main chain; warm-up/main/cool-down transitions break only where the owner already reanchors. A phase name change alone is not evidence of signal failure. No additional GPS filter, freshness threshold or replay engine is introduced.

These links describe supported map continuity, not accepted metres, a completely observed physical path or Ghost Verified evidence. The whole stored run remains available, including recorded warm-up/cool-down points. Rendering must not join across recorded breaks or turn rejected/not-assessed points into supported edges. For old rows, coordinates may exist while route quality and continuity are explicitly unknown; do not infer all original runtime decisions from timestamps, accuracy or current filter defaults. Malformed/unsupported provenance makes the affected route evidence unavailable without repairing the source or hiding otherwise readable frozen detail facts.

**Atomicity and interruption.** Assign point identities once and freeze each raw record with its correct assessed or explicit not-assessed outcome, respecting the owner's actual finalization/freeze boundary. Raw values and provenance commit together with the matching checkpoint/event prefix. ABORT or commit-return uncertainty retains the same immutable point identities, predecessor facts and source timestamps for the existing revision/idempotency guard; Retry does not recapture, renumber or append duplicate points. Later observations remain a separate pending suffix. After process death, only the committed prefix is available; an interrupted recording has no invented stop, final edge or recovered RAM tail. The additive upgrade leaves old run/checkpoint/raw/event/outbox cells unchanged, with null in the new column. Existing nonretryable corruption/read handling and non-destructive open policy remain.

**Normal sharing version.** Newly prepared files from the existing History → Your run, as data → Open Android share sheet flow use AI JSON schema version 2, including older recordings whose point provenance remains absent/null (unknown). There is no format chooser. The disclosure names version 2 and point assessment/continuity metadata in addition to its existing sensitive raw coordinates/UTC/HR warning. Existing v1 files, samples, strict schema, independent consumer support and explicit `ExportRunV1.Project`/diagnostic journal path remain unchanged; v2 does not rewrite old files or local checkpoints.

**AI JSON compatibility.** AI-file format version, checkpoint version, per-point provenance version, journal schema and HC mapping version are separate contracts. This raw-point addition retains checkpoint `SchemaVersion = 1`; the new AI-file envelope is not a new checkpoint or HC mapping version. The current `run-v1.schema.json` sets `locations.items.additionalProperties` to false; checkpoint extension support does not make a new raw-location property compatible with an old v1 validator. The provenance-bearing AI file therefore uses an explicit new schema version 2, with an optional nullable versioned point-provenance field and an independent parser branch. Keep the v1 schema/projector path and its old samples readable without rewriting stored recordings or previously shared files. A v2 consumer also accepts absent/null provenance as unknown for old raw rows, and rejects unsupported provenance versions or invalid/cross-run/forward links without guessing. Preserve existing units, raw values/order, frozen Main/splits and interruption facts. Updating SQLite alone neither changes the current v1 file nor proves v2 support; the schema, projector, sample and independent reconstruction must agree before claiming it. Merged PR109 delivered that v2 schema/projector/sample/parser branch and its normal share-file integration; the explicit v1 diagnostic path remains available. Route projection/rendering is not established by that delivery.

**Frozen HC compatibility.** `HCWritePlanV1` hashes mapping version, run ID, source gate, ordered records and warnings; it does not hash AI-file JSON or raw GPS rows. The existing outbox nevertheless reprojects and compares that HC hash at Prepare and ACK. Route metadata and AI v2 must therefore leave HC mapping version 1, client IDs/version, record payloads/order, provenance notes and warnings byte-equivalent for an unchanged eligible run. In particular, do not add a route-quality warning to that frozen plan, regenerate an old attempt, or gate otherwise eligible delivery on new map evidence. Migration leaves existing `export_queue` status/attempt JSON untouched; normal retries retain the same frozen plan/hash while using only the already specified attempt-token bookkeeping. Null legacy route provenance is not corrupted HC provenance. Existing consent, DEBUG/synthetic/unfinished gates and real-response ACK rules remain unchanged; this slice adds no provider calls, READ permission or HC version.

**Detached Route read boundary.** The next internal seam reads the selected stored ID, original checkpoint and ordered raw/provenance points in one transaction, then projects without database writes or serialize-and-reparse. Route corruption is isolated from the existing summary/detail reader. Whole preserves raw point order and only the explicit supported drawable links; missing legacy provenance produces isolated coordinates with unknown quality, never a guessed continuous track. Do not infer accepted distance, completeness or Ghost verification from geometry.

Whole includes recorded warm-up/cool-down; Main contains Work/Recovery only, with surrounding phase facts delimiting that selection. Main membership requires that recording's frozen boot-monotonic start anchor and coherent effective phase-instance boundaries in the same recorded clock domain. Use the actual applied plan/instance identities, including extensions/skips, rather than subtracting planned warm-up/cool-down or replaying active/pause totals. Boundary support must not be inferred from current process uptime, current timezone, a display elapsed helper or an invented boot identifier. The Synthetic flag remains labelled and is not itself a rejection rule. Missing or contradictory timing, including diagnostic acceleration that does not map consistently to actual boot receipt time, cannot establish that raw point's Main membership; retain an unavailable Main selection rather than guessing, while independently supported Whole facts remain readable. Filter supported links only when both endpoints belong to the selected scope; never create a new predecessor across a removed point or interpolate at a phase boundary. Existing Work/Recovery continuity is retained. A confirmed interrupted prefix may use a coherent current phase and its last committed observation as a prefix cutoff, explicitly not an actual stop; it need not invent a terminal boundary. Missing later cool-down termination does not invalidate an already delimited Main interval. No route filter changes raw data, distance/statistics, AI v1/v2 or frozen HC attempts.

This internal query/projection prerequisite adds no Route action, map placeholder or UI. SDK inclusion/execution, terms/data-flow acceptance and project/key/billing configuration remain separately pending; the approved r4 layout is not permission to activate those services.

**Map boundary.** Google Maps SDK for Android remains the selected provider. An internal run-ID-bound native `MapActivity`/`MapView` is a possible small adapter, not a decided product layout. Key configuration, network/SDK failure or no usable points must leave stored detail, recording and export usable with honest map status. No key/account inspection, Cloud activation, new permission flow or map implementation is authorised by this documentation. [Observable acceptance](delivery-acceptance.md#stored-history-detail-and-route-contract) distinguishes data compatibility from later native rendering.

### Interrupted-prefix local save disposition

Recovery reads only the last committed interrupted row and its unchanged checkpoint. The actual stop remains unknown. An explicit Save recorded part writes only nullable runs.recovery_saved_utc in additive SQLite schema 6; this is a local acknowledgement timestamp sampled during the marker transaction, never a finish, observed stopping time or exact commit-return time. Status stays interrupted. The transaction validates the source first, and a repeated save returns the existing acknowledgement under the same run ID without rewriting plan, checkpoint, raw observations, events or export queue. Success is shown only after EndTransaction returns. Recoverable transaction failures keep Retry save; structural/open/read corruption remains unavailable without repair or an unsupported retry. Navigation never resumes the timer or replaces an active owner. Missing legacy facts remain unavailable. Native migration, rollback/retry, same-ID cold reopen and old-row preservation remain acceptance gates.
